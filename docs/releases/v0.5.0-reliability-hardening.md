# v0.5.0-reliability-hardening

## Highlights

An UNKNOWN Iceberg commit now starts bounded automatic reconciliation in the serial sink path. Subsequent batches and checkpoint advancement wait until valid positive proof exists and COMMITTED metadata is durable. Recovery does not repeat the original ambiguous catalog write. Failed jobs still require operator action.

- Durable PREPARED intents, operation IDs/fingerprints, and exact replay receipts protect restart recovery.
- Metadata cleanup propagates SQL errors, uses an atomic transaction, and preserves unresolved intents.
- Sinks persist confirmed snapshot completion after all required writes are committed and before sending a success ACK. If an ACK is lost, a confirmed receipt permits repeating the completion handshake without replaying snapshot data.
- Split Iceberg workers use transactional ownership fencing for checkpoint, snapshot-state, and commit-intent mutations.
- Shutdown persists the final drained state before releasing the worker lease.
- Recovery progress includes the operation ID, attempt count, last error, checkpoint, and start time.

## Breaking changes and upgrade notes

The minor version increases because legacy snapshot completion now fails closed and split Iceberg workers require the registry and checkpoint stores to share a MySQL endpoint and database. Startup adds completion-version and commit-intent metadata schema. Mixed-version workers and downgrades without a compatibility assessment can bypass these correctness barriers.

Follow the [migration guide](../migration.md#v050-reliability-hardening), including metadata backup, stopping old workers, and reviewing legacy snapshot state and retained intents. There are no new production environment variables; recovery uses the existing job retry policy.

## Verification

Local verification on 2026-10-12:

- **14 integration scenarios passed** in Colima using two MySQL 8.4.11 fixtures, the actual JobManager/CDC/lease lifecycle, and a real Hadoop Iceberg catalog.
- Workers were killed with SIGKILL at commit, recovery, and checkpoint boundaries. Replacement workers claimed expired leases and continued the same submission.
- SIGKILL and restart of the metadata mysqld preserved durable intents and checkpoints. Recovery assertions checked IDs, payloads, snapshot counts, and checkpoint coverage.
- Tests covered SQL COMMITTED persistence failure, cleanup rollback, missing proof, a suspended stale worker, actual row-lock contention, and lease expiry.
- `go test ./... -count=1`, targeted recovery/fencing/shutdown race tests, and the CI UI syntax checks passed.

Commands, fixture isolation, and test boundaries are documented in the [runbook](../../tests/recovery/README.md). Integration flags opt into test fixtures and are not runtime configuration.

## Known limitations

- Catalog persistence uses a real Hadoop filesystem catalog; lost responses and catalog unavailability are injected through test decorators. REST/S3 network faults have not been tested end to end.
- Snapshot/rolling-spool SIGKILL, source-server crashes, host/VM crashes, and all live metadata outage paths are not covered.
- SQL fencing does not cancel stale catalog requests already in flight; missing proof remains BLOCKED. Mode ALL does not gain distributed worker lease fencing.
- The retry budget resets for each process recovery episode. No fleet-wide durable retry budget or new jitter was added.
- External writers, rollback/expiration, composite replace/truncate/Trino operations, and source mutations still require separate assessment. These results do not establish exactly-once behavior across all configurations.
